# G0 contract decisions for implementation handoff

Reviewed: 2026-11-02. Status: **concrete research recommendations**, not frozen OpenAPI or implemented validation. Consumes [1.pdf](../../1.pdf), the [draft HTTP/service contract](../superpowers/specs/2026-11-02-corevapt-contracts.md) and the [architecture review](ARCHITECTURE_FIT_REVIEW.md). These decisions resolve previously unspecified semantics so the contract owner can author executable schemas without inventing them independently.

## 1. Contract technology and authority

Use **OpenAPI 3.1.2** for the initial HTTP document and JSON Schema 2020-12-compatible domain schemas. This is an interoperability choice, not a claim that 3.1.2 is the latest specification. Verify chosen FastAPI/client-generation/validation tools accept this version before pinning; adopt a different compatible 3.1 patch through the contract change process if necessary. Keep `contracts/openapi.yaml` as the external source of truth and generated FE types/backend DTO mapping as consumers. [OpenAPI 3.1.2](https://spec.openapis.org/oas/v3.1.2.html), [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/release-notes).

OpenAPI can describe an API before implementation; it does not prove a server enforces it. A YAML parse is not complete OpenAPI/schema validation. [OpenAPI lifecycle guidance](https://www.openapis.org/what-is-openapi).

No application contract file or validator was generated by this research pass. The environment check found YAML/Pydantic available but no `jsonschema` or `openapi_spec_validator` module in the checked Python environment. No package was installed. G0 remains unpassed until actual schema/example/semantic checks and owner review occur.

## 2. First-slice destination and profile model

Choose one exact lab asset per assessment for the initial vertical slice; do not promise a subnet/discovery platform. Multiple permitted TCP ports are allowed. Wider targets, UDP and IPv6 live execution remain disabled until explicit schema/network acceptance, although canonicalization and negative tests must reject them correctly. This is a proposed scope reduction, not a PDF restriction or a statement that IPv6 can be ignored by the network guard.

`AssetIdentity`: server-generated UUID plus `host` (lowercase canonical ASCII hostname), `ipv4` (canonical dotted-quad), `aliases` (explicit exact hostnames), and `authorization_ref_id`. V1 binds one hostname to one authorized `/32`; no wildcard hostnames, arbitrary URLs, implicit suffix matches, CIDR expansion or client-selected resolver. If the lab provides an IP without a hostname, the hostname may be null and URL host is the bound numeric IP.

These `AssetIdentity` constraints apply to the live target. Imported observations use an `ObservedAssetIdentity` with source address family `ipv4|ipv6|hostname|unknown`, raw identity, nullable canonical identity and nullable authorized-asset link. Unsupported or unresolved historical identities are preserved; they do not become live scope. Likewise, imported service protocols/locations may be broader or unknown and are not coerced into the live TCP profile.

`ServiceIdentity`: `asset_id`, `transport=tcp`, integer `port` 1–65535, nullable `scheme=http|https`, and source observation IDs. A port number alone does not prove HTTP. Scheme/port must match the scope and observed evidence; do not silently turn HTTP 80 into HTTPS 443.

`WebLocation`: normalized scheme/host/port/path, original raw URL locator, optional method/parameter, and redaction metadata. Preserve distinctions that affect identity; do not collapse query values or treat redacted strings as a unique source key. Nmap service observations have no synthetic web path or invented vulnerability/CVE.

| Profile | Typed inputs | Fixed behavior | Denied inputs |
| --- | --- | --- | --- |
| `nmap_discovery_v1` | asset_id, sorted unique TCP port list, deadline_seconds | TCP connect plus bounded light service detection, numeric bound IP, no name resolution, XML artifact | raw argv, script names, arbitrary flags, OS/aggressive mode, additional target |
| `zap_baseline_v1` | asset_id, scheme, port, root_path, deadline_seconds | Packaged baseline AF-only, bounded spider/passive analysis, traditional-json report, exact authorized origin; launcher-owned fixed `-P 8090` and `-z -silent`; reject legacy fallback | active/full/API scan, caller-supplied `-z`, `-n`, `-U`, hooks/scripts, `--autooff`, arbitrary config URLs/options, unrestricted crawl target |

The worker derives actual invocation from profile version and a trusted permit. The model proposes catalog IDs and typed parameters; the browser never sends CLI. V1 accepts only an origin-wide authorized web scope with root path `/`. A path-only authorization is rejected because packaged baseline behavior can reach the origin root; narrower path scope needs separate enforced acceptance and does not establish authentication/API coverage. Native import kinds remain `nmap_xml|zap_json|greenbone_xml`, with exact format selectors from [scanner decisions](SCANNER_READINESS_DECISIONS.md).

## 3. Bounded defaults to freeze and test

These are proposed conservative configuration defaults, not scanner performance predictions or organizer limits. Effective limits are the minimum of configured caps, approved ROE and remaining assessment budget. Changing them requires explicit versioned configuration; the model cannot raise them.

| Surface | Proposed limit | Required error/outcome |
| --- | --- | --- |
| Assessment targets | 1 IPv4 `/32`; up to 16 explicit TCP ports | 422 if unsupported target count/type; exclusions always win |
| Request/message | 4,000 Unicode characters; no client actor/source override | 422; persist analyst content as data, not permission |
| Message/timeline list | default 50, maximum 100 items | Stable bounded cursor; 422 for excessive limit |
| One plan result | at most one next action; rationale up to 2,000 characters; up to 32 basis IDs | schema/semantic rejection; no action if unsupported |
| Assessment action budget | 8 actions; one active attempt per assessment and one live scanner globally on the initial host | stop/partial with explicit reason, no implicit rerun |
| Model policy | 8 calls per assessment; provider token/output/time caps set in provider config | typed failure/finalization; evaluation budget is separate |
| Native upload | 20 MiB raw bytes; controlled content types and original bytes retained | 413 before parse; 415 unsupported media; 422 malformed schema |
| Parser | depth 64, 10,000 records, 10-second wall budget in isolated parser process | resource_limit diagnostic, no fabricated empty success |
| Scanner deadlines | proposed 120 seconds Nmap, 180 seconds ZAP; 5-second termination grace | timed_out/partial receipt, bounded group/container cleanup |
| Report snapshot/render | 10 MiB snapshot; 30-second render; 512 MiB memory | render_failed; immutable snapshot retained, never ready |

Validate deadlines against actual pinned tool startup and lab size before enabling live availability. If the legitimate fixture exceeds a limit, update the cap deliberately and rerun resource tests; do not truncate silently. Raw parsing and rendering limits are separate from a report's semantic completeness. Native raw output caps must agree with storage quotas and launcher output caps.

## 4. Messages, planning and idempotency

Separate append from inference. `POST /messages` persists analyst content and returns the message/revision; it does **not** invoke a model or create a scanner execution. The UI explicitly requests a plan after appending. The initial assessment request remains the initial request; later intent-bearing messages increment state revision. Non-mutating explanations must not accidentally invalidate a still-valid approved action: define message `intent=assessment_request|clarification|comment` and revision effects in G0, with server classification/validation rather than trusting an arbitrary client override.

For the first slice, make all analyst messages intent-changing conservatively; retain old actions as stale, never silently dispatch them. A future classification optimization requires its own compatibility/test update. This rule is intentionally simpler than inferring that a changed natural-language request is harmless.

Require `Idempotency-Key` for message append, plan requests, import creation, execution creation and report creation. Scope the key by authenticated actor, assessment and operation. Same key+canonical body returns the original resource/outcome; same key with a different body returns 409. A browser reconnect does not create a second message, model call or scanner attempt. Retain completed key records for the assessment lifetime in v1; expire abandoned pre-commit reservations under a documented no-side-effect policy rather than an arbitrary short TTL.

The plan call is initially synchronous and bounded by the configured provider/overall deadline, without holding a DB transaction across inference. Persist the request reservation/decision identity first, call the model, then compare state/scope revision before committing a valid proposal. Concurrent duplicates return the existing operation state; do not spend the budget twice. A provider timeout/ambiguous response is recorded and not invisibly retried; a new bounded retry has a new attempt linked to the original.

G0 must define the synchronous in-progress duplicate response (409 `operation_in_progress` with a stable decision ID and retry guidance), completed 200 result, stale 409, typed dependency 503 and idempotent reuse of prior failures. Adding asynchronous planner jobs later changes the job-kind contract and UI; do not quietly add a fourth generic job kind.

## 5. Proposal, dispatch and immutable identity

`PlanResult` is a tagged decision `propose|ask|stop|inconclusive`, with `source=llm|deterministic`, `state_revision`, rationale, basis IDs, unknowns, remaining budget, and at most one typed proposal. A stopped/asked/inconclusive result has no dispatchable action. The model does not choose actor, authorization decision, canonical hash or execution identity.

Bind the server action hash to action ID, assessment ID, profile ID/version, canonical asset/destination and parameters, effective scope hash/version, sorted basis IDs, expiry and reserved budget. The worker receives a bound reservation from `authorize_dispatch`; only the trusted launcher calls `authorize_start` after preparation to revalidate and consume the grant. Public execution remains queued through preparation and becomes running only when an actual scanner-start receipt is observed; generic job running can include preparation.

Human-readable rationale belongs to its immutable decision record; it is not a place to hide executable options. A grant references that exact hash and is consumed once for its authorized attempt.

Choose a documented domain-specific canonical JSON encoding for v1: ASCII keys/IDs/normalized hostname/IP/time values, integers/booleans only in authority-bearing fields, sorted unordered sets, UTC-second timestamps `YYYY-MM-DDTHH:MM:SSZ`, lowercase canonical UUIDs and no floats/NaN. Byte encoding is UTF-8 and separators/key ordering are fixed. Do not call ordinary `sort_keys` output RFC8785/JCS-compliant for arbitrary Unicode/numbers. JCS is a relevant reference for reproducible hashing, not a requirement imposed by the contest. [RFC8785](https://www.rfc-editor.org/rfc/rfc8785).

Publish canonical-byte/hash golden vectors and mutations at G0. IDs, timestamps, URLs and port sets must normalize before hashing. Scope authorization text can contain Unicode, but the authority-bearing scope representation uses an immutable ROE reference ID plus normalized effective fields; the original ROE document is retained separately with its own byte hash.

## 6. Separate lifecycles

| Record | Proposed states | Semantics |
| --- | --- | --- |
| Generic job | queued, running, succeeded, failed, cancelled, unknown | Scheduler state only; resource outcome remains authoritative |
| Scanner execution | queued, running, succeeded, partial, failed, timed_out, cancelled, execution_unknown | Existing contract; receipt/completeness and adapter exit semantics determine outcome |
| Import | queued, parsing, succeeded, partial, failed | Parser warnings/record bounds and raw references retained |
| Report | pending, rendering, ready, failed | Ready only after immutable PDF artifact/hash is committed |
| Action approval | pending, granted, rejected, expired, consumed, stale | Grant cannot replace permission or be reused for a modified action |
| Analyst disposition | needs_review, accepted, rejected | Does not change source observations or establish exploit confirmation |
| Finding validation | observed, suspected, confirmed, rejected, needs_review | Confirmed requires attributed method and supporting evidence |

Generic job unknown does not force a safe pure import/render retry to be forbidden; handler-specific reconciliation proves whether it can resume/reparse safely. An unknown scanner attempt does prohibit blind rescan. Out-of-scope denial is an authorization event rather than scanner failure.

A scope edit and pre-dispatch authorization serialize through the same scope/action record discipline. Already-sent traffic cannot be revoked; cancel affected running attempts and record that limit. A DB permit alone does not solve the delay before external start: [safety decisions](SAFETY_RECOVERY_PILOT_DECISIONS.md) define the launch fence and receipt protocol.

## 7. Risk and report semantics

Store CVSS score, vector, version and source independently from local review priority. Exposure, asset impact and exploitability are typed known/unknown inputs with attributed analyst rationale or observation IDs and timestamps. Confidence keeps its scanner-specific method/raw value; it is not converted into a common probability.

Proposed priority is an ordinal review queue, not an invented risk score: `review_first|review_next|routine`. A credible high/critical source severity, applicable exploitation evidence, or medium severity on a reachable high-impact asset puts an item in review_first. Low confidence adds validation urgency rather than automatically downgrading severity. Missing essential context or source severity requires review_next at minimum, with explicit unknown flags. Routine is only assigned when supported low/informational severity and known context justify it; source data is never overwritten. Freeze exact tie-breaking/source conflict rules and the 12 labelled comparison expectations before coding.

Report counts distinguish observations, canonical candidate findings, accepted/actionable findings, rejected dispositions and unresolved review. A rejected finding can be excluded from the main actionable list but remains in the snapshot/audit/appendix with its source evidence. A report with failures/pending review may be produced as a disclosed draft; a `ready` PDF file is not automatically `client_ready`. Require attributed analyst release review for that label.

## 8. G0 closure checklist

The contract owner must produce, not merely promise:

1. OpenAPI for every route in the existing inventory, complete domain/profile/job/approval/risk/snapshot schemas, strict extra-field policy and operation IDs.
2. Valid/invalid fixtures for planned/available/error/empty/partial/unknown/historical/mixed-source states, including all retry/revision/hash cases.
3. Full OpenAPI validation plus JSON Schema validation of fixtures, with format enforcement for UUID/IP/time where required.
4. Semantic tests for foreign/missing evidence, revision conflicts, profile preconditions, timestamp windows and known/unknown context. Valid JSON is insufficient.
5. Canonical action/scope hash vectors with byte-for-byte cross-language verification, request digests and operation idempotency behavior.
6. Backend and user-appointed frontend owner review of the route-to-view map; generated types validated against real fixtures, not handwritten mock DTOs.

No item is marked passed by this research. G0 can be developed without organizer targets, paid model calls or live scanner execution; those prerequisites gate later features. This distinction allows independent work without representing design evidence as runtime acceptance.
